Speed Test Notifications — proposal

What exists today. The wallpaper change already does progress reporting, and it does it in a specific way: the notifications app subscribes to the wallpaper.state domain event and builds a bespoke card it mutates in place — one card, a 4-step checklist, an indeterminate ProgressBar.pulse() while busy, then set_fraction(1) and a 5 s auto-dismiss. It never calls Notify and never uses replaces_id.

What already exists for us. publishSpeedTestFinished() is already wired in speedtest-service.ts and emits speedtest.finished on org.dotfiles.Events — but nothing subscribes to it. So the plumbing is half-built: a producer with no consumer.

The proposal. Extend that event to a speedtest.state topic with phases (starting → measuring → done | error) and give the notifications app a progress card modelled directly on the wallpaper one. One card, mutated in place, auto-dismissing — not a burst of separate toasts.

Design decisions, and why

  • One card mutated in place, not a burst of toasts. This copies the wallpaper model exactly. A run is a single logical operation; four separate notifications would be noise and would each need their own dismissal.
  • Progress bar pulses rather than showing a percentage. speedtest-cli gives us one JSON blob at the end — it reports no intermediate progress. A fake percentage would be a lie. The pulse is honest: we genuinely do not know how far along it is.
  • Steps are speculative-but-scoped. Latency → download → upload is the real order the tool performs, and it gives the eye something to land on. The copy never claims a number it lacks.
  • Auto-dismiss: 5s on success (like wallpaper), sticky on failure. Success is informational and self-evident from the panel; a failure needs a decision, so it stays like the capture tool's critical cards.
  • Result mirrors the panel's new three rows — Download / Upload / Ping as separate cells, so the card and the panel read identically.
  • Server name in the body for context, matching the detail level of the capture cards.

Implementation shape

  • Extend the existing event: speedtest.finished → speedtest.state with { state, trigger }, mirroring the wallpaper.state contract in contracts/event-contract.json. Note: the wallpaper card already reads a stage key that is not in the pinned contract — I would not repeat that; the new keys need adding to the contract, or the drift gate will fail.
  • Producer: speedtest-service.ts emits started / finished / error. It already has publishSpeedTestFinished and the exact state transitions needed.
  • Consumer: a speedtest-events.ts beside the existing wallpaper-events.ts, and a speedtestUpdate() handler in NotificationsWindow.tsx built from the existing wallpaper card code.
  • Setting: add notify_on_test: boolean to SpeedTestConfig + DEFAULT_CONFIG + the loadConfig merge, and a row matching the existing run_on_connect pattern (settings-stc-row + WifiSwitch). Gating happens in the producer, so nothing is built or spawned when it is off — the same fail-open rule the capture tool uses.
