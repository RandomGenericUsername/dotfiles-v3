Pairing flows

The answer, short: Just Works devices pair the same way in every option — the panel's own agent handles those and nothing else is involved. PIN-requiring devices are the entire question: BlueZ only asks an agent whose declared capability satisfies the method, so it never asks the panel (which registers NoInputNoOutput). The only capable agent on this system is blueman-applet. So yes — stop autostarting blueman and PIN pairing stops working, and no other option loses it.

How to read the strips: each one is a scenario, left to right — tap Pair, wait, land. The panels are 312 px like everywhere else, so ×1 is the true size. Where two options look identical for part of the strip, that is drawn as identical, because that is exactly what the user sees.
A · Just Works TOZO NC9 — the same in A, C and D. Nothing to decide. The panel registers its own NoInputNoOutput agent, which auto-accepts, so BlueZ has no reason to ask anyone for a PIN. No second window appears, in any option.

Side by side. All three options give a clean bar. They differ only in what happens to a device that wants a PIN — which is why this is worth getting right before touching the autostart.
Option Bar stays clean PIN / passkey pairing The user must What it costs
A — keep the applet,
hide its tray icontask 8.1		 Yes Works
The applet's agent answers the PIN — in the applet's window.		 Tap Pair, then switch to the other window and type the PIN. One window switch. The PIN UI is not where you clicked.
C — suppress the autostarttask 8.2 Yes Broken
No capable agent on the bus. After 30 s the row fails with Pairing timed out.		 Notice the failure, then open Blueman and pair from there. A real capability loss for PIN devices, plus a manual detour to recover.
D — PIN entry in the panelnot scheduled Yes Works
In place, in this panel. No second window at all.		 Type the PIN in the panel. The largest change by far: agent capability → KeyboardOnly, a PIN field, popup keymode NONE → ON_DEMAND. An explicit non-goal today.
Verdict — option A. Keeping blueman-applet running and hiding only its tray icon is the one choice that gives up nothing. Just Works devices pair through the panel's own agent either way, so A is not buying PIN support at any cost to the common case — it is buying it for the cost of one window switch, and only for devices that actually ask. C buys the same clean bar by deleting a capability: pairing still looks like it is working for a full 30 seconds, and then it fails without explaining itself. That is a worse trade than it appears, because the device you most need to pair — one you have just unboxed and are standing over — is exactly the device that will want a PIN. D is the only option that removes the blueman dependency and puts the PIN where you clicked; it is also several times the work, it is not scheduled, and PIN entry in the panel is written down as a non-goal in proposal.md. If the window switch in B ever turns out to annoy you in practice, D is the answer — but take A now and revisit.
Honesty note — what is drawn from code and what is not. Every panel above is a real state of the popup as it ships today, and the receipts are below. The one thing this page cannot show you is the existence of the applet's agent: BlueZ 5.87 exposes no GetAgents and the system bus cannot be eavesdropped unprivileged, so "a capable agent is registered while blueman-applet runs" is blueman's documented behaviour, taken on trust rather than measured. Scenarios B and C both rest on that premise. If it were wrong, B would fail exactly the way C does — which is the honest size of the risk.
panel agentsettings-panel/bluetooth-agent.ts — RegisterAgent(…, "NoInputNoOutput") then RequestDefaultAgent. Just Works: it auto-accepts and is never asked for a PIN.
routing ruleBlueZ asks only agents whose declared capability satisfies the method. This is BlueZ behaviour, not something in this repo, and it is why step 2 of C cannot resolve.
30 secondsservices/bluetooth-service.ts — WATCHDOG_MS = 30000 per action, surfacing "<action> timed out", hence Pairing timed out.
keymodecomponents/bluetooth/BluetoothPopup.tsx — Keymode.NONE on both windows, and there is no entry to type into. That is what D would have to lift.
the appletAutostarts from /etc/xdg/autostart/blueman.desktop and is the process that keeps a capable agent registered. Documented behaviour — not verifiable from this machine, for the reason above.
