Terminal chrome, btop, and what “window” actually means

A skin is paint, geometry, type and ink. A terminal emulator and a TUI each expose only part of that vocabulary. This review separates what is already live, what a skin can honestly project next, and what must stay app-owned — then maps the six surface names (five real, one deferred) to real consumers.

live now blocked by units / no token deferred, not rejected palette = colors.*

kitty

Palette-only today. colors.kitty is included, new windows read it, open windows reload by SIGUSR1. The only further honest knob is font_family; sizes and paddings are points, not skin px.

btop

Palette-only permanently. The theme surface is 48 colour keys. There is no radius, padding, type or rhythm key to project, so geometry/type are not “missing” — they do not exist.

surface roles

No new surface.window now. panel is the outer surface; card is an inner card, including notification cards on the layer-shell stack. A future window role is deferred with criteria.

2 · btop: palette only, and genuinely nothing else

format target: theme

btop's theme is a key/value colour table. The 48 documented keys cover backgrounds, foregrounds, selection and meter gradients. Radius, spacing, font family/size and transparency are not theme keys — they are btop's own layout or the host terminal's job.

Not applicable — no skin geometry or type

These are not deferred features; btop has no theme surface for them.

not applicable
Corner radius
No theme key. btop draws its own boxes; the terminal font and cell grid decide the shape.
Padding / spacing / rhythm
btop's layout is app config, not a skin token. No surface.*.padding consumer exists.
Font family / size
btop inherits the terminal font. There is no btop font knob in the theme.
Blur / shadow / opacity
Terminal/compositor compositing only. btop's theme is opaque hex by construction.
Graph symbols / presets / update_ms
Real btop settings, but app-owned config — never a skin projection.
Decision: keep btop palette-only. A skin .theme would need literal hex for all 48 keys — that is the palette producer's job, not the skin plane's.

3 · surface roles: panel is outer, card is inner

five real roles · one deferred

The names are not synonyms. panel is the outer painted panel/window; card is an inner card. A notification is a card on a transparent layer-shell stack, not an outer window. The dashed block is the deferred surface.window idea, not a current token.

surface.panel · outer
AGS bar panel · rofi window · wlogout window
surface.card · inner
notification card · rofi mainbox · dialog card
surface.control
button / entry
surface.cell
list row / tile
surface.pill · badge / chip / capsule
surface.window · deferred
Only for a real, painted outer toplevel with semantics that panel cannot honestly express. No consumer meets that bar today.

surface.panel — outer surface

Owns the outermost frame: bg, border, radius, padding, shadow, blur. Maps to rofi window, wlogout window, the AGS bar settings panel. It is not limited to the bar.

surface.card — inner card

Owns an inner content card: notification cards, rofi mainbox, dialog cards. Notification cards live on a layer-shell stack; the stack window is a transparent container, so the card is not an outer surface.

surface.control — compact control

Button/entry/row-action paint and type. Distinct from a card: a control is interactive and owns font-size/font-weight.

surface.cell — row / tile

List row or tile surface, with its own hover-bg. It may be borderless; it is not a card and not a control.

surface.pill — badge / chip

Capsule identity: own radius, padding, font size and letter spacing. A pill is deliberately not a rectangle and is never host-inheritable.

surface.window — deferred

Would need a real painted toplevel, distinct semantics from panel, a token justification, a host-policy decision and a full migration. None of those exists today.

Why not “fix” card to mean window? The notification source says it directly: “Notifications are cards, not windows” and the cards take surface.card.*. The layer-shell window is a transparent overlay container. Calling the cards panel would give every notification the outer frame and shadow; adding window would still describe the wrong level. The current split is semantically correct.

4 · Criteria, decision and next slice

design only · no schema change

kitty — criteria

  • K-1 include current/colors.kitty; new windows and SIGUSR1 reload stay.
  • K-2 no skin artifact ships in this slice; conf stays reserved.
  • K-3 the px→pt blocker is proven by a parse probe.
  • Next slice: font_family only, first-family rule, kitty +runpy gate.

btop — criteria

  • B-1 exactly the 48 colour keys; no radius/padding/type.
  • B-2 btop.conf stays two settings; no skin .theme.
  • B-3 graph/preset/update settings remain app-owned.
  • Next slice: none.

roles — criteria

  • W-1 panel is the outer surface.
  • W-2 card is an inner card; notifications are cards.
  • W-3 no surface.window schema/token/host path now.
  • W-4 revisit only with a real painted toplevel + distinct semantics + migration.

Decision

  • a) no new role: panel is the outer surface. Chosen.
  • b) surface.window for a future real toplevel. Deferred, not rejected.
  • Aliases are not roles: if it only renames panel, document it, do not add it.
Next implementation slice (optional, assets-only): a kitty.conf.j2 that projects only {{SKIN_TYPE_FONT_FAMILY}}, registers kitty/conf in the assets required artifacts, and parses the render with kitty +runpy load_config(..., accumulate_bad_lines=b) asserting b == []. No runtime/schema change. btop and surface.window have no slice.
