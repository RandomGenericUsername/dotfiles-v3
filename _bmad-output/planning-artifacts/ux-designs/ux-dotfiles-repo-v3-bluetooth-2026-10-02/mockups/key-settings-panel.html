Why the tile glyph stays, and why it is not the header control

CapabilityTile keeps IconToggle on the main-view tile only, where the glyph has 34 px of room and no header to share with. Two different jobs, two different slots: the glyph says which capability this is, the switch says is it on.

IconToggle is a Gtk.Button, so its clicked signal fires only on genuine user activation — it does not carry the notify::active self-oscillation hazard WifiSwitch was written to defeat. Both stay. But both now forward an explicit value via setBluetoothPowered(enabled) instead of a blind toggleBluetooth() read-modify-write: two surfaces can now both mount a toggle, and a stale read is a rare but real way to write the wrong value.

The pinned-header rule. SubviewHeader.tsx exists because of a bug that has already been paid for once: the header used to be rendered by WifiView and BluetoothView, i.e. inside the scrolled window, so it scrolled away with the content and the two surfaces behaved differently despite sharing one NavHeader component. Same components, two different containers; the container is what decides whether the header stays put. The subview scroll height is 339 px (geometry.subview-scroll-height) — the panel's own budget, distinct from the popup's maxContentHeight 420.

Parity is not about looking alike; it is about doing alike.

The capability glyph is not lost. BluetoothToggle is not deleted — it is demoted. CapabilityTile keeps IconToggle on the main-view tile (mock 1, above), and the header slot becomes the switch (mock 2, left). One glyph, two jobs, two homes, zero new primitives.
