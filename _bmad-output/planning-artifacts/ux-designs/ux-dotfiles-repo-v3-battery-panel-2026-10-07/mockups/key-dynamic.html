④ The model is dynamic

The declaration must survive the daemon's runtime: profiles are renamed, created and removed, and a future daemon may add a tier this build never heard of. Each proof below is rendered as the panel actually draws it — because resolution is tier → mode → glyph, not a hardcoded name list.
← index · dynamic-rename · dynamic-new-variant · dynamic-unknown · dynamic-three-variants
The glyph never tracks the name. profile_name is the user's; the tier is the daemon's; the art belongs to the mode the tier declares. Rename, add and remove are therefore no-ops for the artwork.

What the daemon returns

"active_profile": 1, "profiles": [ { "profile_name": "Powersave++", "base_profile": "Superpowersave" }, { "profile_name": "Powersave", "base_profile": "Powersave" }, { "profile_name": "Balanced", "base_profile": "Balanced" }, { "profile_name": "Performance", "base_profile": "Performance" }, { "profile_name": "Performance++","base_profile": "Ultraperformance" }, { "profile_name": "Meetings", "base_profile": "Powersave" } <— new ]

No code changes: the deployment groups profiles by looking up each base_profile in the declaration, so Meetings joins Powersave mode because its tier Powersave is listed there. Two profiles on the same tier are two sibling variants — same level, same glyph, distinguished by name.

Fallback rules

Two channels: the neutral shape says “undeclared”, the words unmapped tier say the same. A profile is never dropped and never rendered blank.

This is the pressure valve the two-level model buys: any number of profiles can pile onto a tier without ever demanding new artwork or a wider panel. The mode count is bounded by the declaration; the variant count is unbounded and simply wraps.
