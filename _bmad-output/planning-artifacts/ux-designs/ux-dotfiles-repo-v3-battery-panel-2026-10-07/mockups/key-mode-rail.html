② The mode rail

A mode owns a glyph; a variant is a selectable profile sitting on a tier that mode declares. The rail therefore shows one cell per MODE — three cells — and the selected mode's variants appear as a second-level control only when that mode has more than one. The selected profile's name, mode and tier are stated once, under the selector.

Why three cells, not five. The owner rejected a flat five-cell rail with five glyphs. Two tiers of one mode share one glyph by design, so the rail groups by mode and the variant is a sub-choice. See key-declaration.html for the declaration itself.

The mode cell is a button, so the whole target is clickable and keyboard-focusable, exactly like PowerProfileRow ships today. sensitive = powerReady is unchanged: before the daemon answers, the whole selector dims to 0.5 rather than pretending a mode is active.

Balanced declares one tier, so there is nothing to choose and no control is drawn. The absence is the design: the rail does not render a one-option picker, and the panel stays shorter. Selecting this mode selects its single variant directly.

The control-visibility rule

Selected mode declaresVariant control
1 variant (Balanced)not rendered
2 variants (Powersave, Performance)rendered, active pill marked
3+ variants (a mode that grew)rendered, wraps if needed
mode before the daemon answersrendered from the last good read, dimmed

This is the rule the owner's model implies: a variant is a real choice only when there is more than one. A one-option segmented control would be decoration, not a decision.

unlisted mode · unmapped tier
A future daemon adds a tier this build never declared. The profile does not vanish and no blank cell is drawn: it gathers under an Unlisted pseudo-mode that carries the labelled neutral glyph, and the meta line says unmapped tier. The profile stays selectable; the gap is visible on the surface, not in the logs.

Fallback rules

CaseSelector renders
tier declared by a modethat mode's real glyph; profile joins as a variant
tier not declared anywherethe labelled fallback, under an Unlisted pseudo-mode
tier missing / emptyfallback + the meta line says unmapped tier
profile renamedthe mode and glyph do not move; the variant label does
profile created at runtimejoins its tier's mode as a new variant, no restart

Two channels per state: the shape says “I don't know this tier”, the words unmapped tier say the same. So an unselected fallback and an unselected real mode are distinguishable by shape alone, without colour.
