③ The declaration

The rejected model was a flat rail with one glyph per profile — five cells, five glyphs. The owner's model is two-level: a mode owns a glyph, and a variant is a selectable profile sitting on a tier the mode declares. Three glyphs, five selectable things. The grouping cannot be inferred from a profile's text or tier; it is declared. This page draws that declaration and its consequences.
← index · decl-modes · decl-shared-glyph · decl-resolution · decl-fallback · decl-not-inferred
The stable key is the tier. The declaration groups tiers; a profile resolves to a mode through its base_profile. Renaming a profile never touches the art, because the art hangs off the mode the tier selected, not off the name.

Two tiers point at one glyph. Powersave and Superpowersave both hang off the leaf; Performance and Ultraperformance both hang off the engine. That is the whole reason the run no longer draws five glyphs: the artwork lives on the mode, so any tier the mode declares shares it automatically. Balanced declares one tier, so it has nothing to share — and, on the panel, nothing to choose.

Why the relation is declared, not inferred · decl-not-inferred

Three facts force the grouping to be an explicit declaration rather than a rule over a string or a single stable field. Each one is drawn below.

✕ Infer from profile_name (strip the ++)

Performance++ strip “++” → performance → would pick the Performance glyph (wrong) ✕ real tier is Ultraperformance

UpdateProfileName makes profile_name arbitrary; the moment the profile is renamed (e.g. Performance++ → Showtime) a suffix rule has nothing to strip and the resolution breaks. The name is the user's, and it is editable.

base_profile IS the stable key — users cannot rename it — but it yields five distinct tiers, not three: live values are Powersave++ → Superpowersave and Performance++ → Ultraperformance, and the daemon treats them as genuinely different tiers. A tier-only rule therefore asks for five glyphs, which is the wrong answer. The grouping is an explicit declaration that says which tiers are variants of one mode.

✓ Declared — the model this run renders

stable key = the tier declaration = tier → mode glyph hangs on the mode undeclared tier → fallback

The key that resolution uses is the tier (rename-proof); the thing that says which tiers share a glyph is the declaration. An unlisted tier falls to the labelled neutral glyph rather than disappearing, and the rail grows a mode cell only when the artwork genuinely differs.

The declaration, literally

# the deliverable's core — modes, glyph, and the tiers each owns mode "Powersave" glyph: leaf tiers: [Powersave, Superpowersave] mode "Balanced" glyph: scales tiers: [Balanced] mode "Performance" glyph: engine tiers: [Performance, Ultraperformance] # resolution: profile.base_profile → the mode that lists it → that mode's glyph # unlisted base_profile → the neutral fallback → "unmapped tier" # variant control renders ⇔ the selected mode declares > 1 variant

key-mode-rail.html renders this declaration as the selector. key-dynamic.html proves it survives renames, new profiles, undeclared tiers and a mode that grows to three variants.
